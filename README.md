# Turbo Rating

Минимальный MVP: асинхронный `OpenDotaClient` на `httpx`, проверка API
и локальное хранение игроков и матчей в SQLite через стандартный `sqlite3`.
Telegram-бот на aiogram 3 поддерживает `/start`, `/add`, `/profile`, `/matches`,
`/sync`, `/rating`, `/history`, `/stats`, `/top` и `/prizes`. Turbo Rating зависит только от побед и поражений в Turbo.
Пока бот запущен, привязанные аккаунты автоматически синхронизируются.

Требуется Python 3.11 или новее.

## Ежемесячные сезоны и призы

Кнопка «💰 Призы» и `/prizes` открывают общий экран: 3 000 ₽ за первое место,
2 000 ₽ за второе, 1 000 ₽ за третье, дата окончания, обратный отсчёт и текущий top-3.

Каждый календарный месяц — сезон `YYYY-MM` по **Europe/Moscow (UTC+3)**.
Границы хранятся как Unix timestamps: начало включительно, начало следующего
месяца исключительно. Сентябрь заканчивается **30.09.2026 в 23:59:59 МСК**,
октябрь начинается **01.10.2026 в 00:00:00 МСК** (30 сентября 21:00 UTC).
Расчёт не зависит от часового пояса ОС и работает на Windows без базы tzdata.

При запуске обновлённого приложения `init_db()` повторяемо добавляет сезонные поля.
Существующие `ratings` и уже учтённые `rating_history` относятся к `2026-09`:
начальные/текущие значения, калибровка и начисления не пересчитываются.
У `matches.season_id` сохраняется фактический месяц `start_time`, в том числе для
старой истории до сентября. Уже начисленная история — часть перенесённого
сентябрьского баланса, её повторного начисления нет. Сентябрьская калибровка
сохраняется до перехода; с октября все новые сезонные рейтинги начинаются с **1000**.

`seasons` хранит `season_id` (PRIMARY KEY), `starts_at`, `ends_at`, `closed_at`.
`ratings` остаётся текущим балансом аккаунта с `season_id`; `rating_history` хранит
сезон каждого начисления. Существующая `season_final_standings` расширена полем
`season_id` с UNIQUE-индексом. Одна неизменяемая JSON-запись на закрытый месяц содержит
всех игроков: `account_id`, `nickname`, `final_rating`, `final_position`,
`matches_played`, `wins`, `losses`, исходный рейтинг и калибровку. Статистика снимка
считает учтённые рейтинговые Turbo-матчи. Отключённые аккаунты сохраняются с
`final_position = null`; места получают активные привязанные аккаунты, как раньше.
Равенство TR разрешается по `account_id ASC`, несколько Telegram-привязок не дублируют игрока.

`ensure_current_season()` в одной транзакции `BEGIN IMMEDIATE`:

1. Сохраняет полный снимок завершившегося месяца, включая пустой сезон.
2. Помечает сезон закрытым и создаёт следующий календарный месяц.
3. Переводит существующие `ratings` в новый месяц с initial/current TR = 1000
   и нулевой калибровкой. Новые аккаунты инициализируются при первом входе.

При ошибке откатывается вся операция. Уникальные индексы защищают месяц, снимок
и единственный открытый сезон; триггеры запрещают изменение/удаление снимков.
Повторный вызов не сбрасывает уже заработанные очки. После простоя пропущенные
месяцы закрываются последовательно. Старые снимки прежнего единственного дедлайна,
если они были, остаются нетронутыми под исходным `season_end_at`.

Переход запускает отдельная задача `turbo-seasons`: она ожидает границу месяца
с проверкой часов не реже минуты, независимо от задержек OpenDota. Проверка также
выполняется при запуске, sync, чтении рейтинга/топа и изменении имени/привязки.
Если бот выключен в полночь, переход произойдёт при следующем запуске до запросов API.

Матч относится к месяцу **начала матча**, независимо от времени sync или окончания.
Поздние матчи закрытого месяца сохраняются со статистикой, но TR не начисляется,
снимок и рейтинг нового месяца не меняются. Пропущенный performance закрытых сезонов
автоматически не восстанавливается; ответ запроса, пришедший после закрытия,
игнорируется. Начисление, пересёкшее границу внутри транзакции, откатывается перед
снимком. История матчей остаётся за 7 дней, новые сверху, старые записи сохраняются;
даты показываются по Москве, начисленные ранее TR остаются исходными.

`/top` и профиль используют текущий сезон. Стрелки места не сравнивают разные месяцы.
«Призы» показывает условия текущего месяца и итоги предыдущего из сохранённого
снимка. `get_final_standings('2026-09')` возвращает полный финальный топ;
`get_season_results('2026-09')` — также результаты отключённых аккаунтов.
Без аргумента `get_final_standings()` возвращает последний закрытый сезон (либо None).
`get_leaderboard_at()` для закрытого месяца читает фиксированный итоговый топ,
`get_rating_at()` восстанавливает баланс по сохранённой истории этого месяца.
Рекорд остаётся за всё время; изменение TR за период ограничено текущим сезоном.
Формула ±25 + performance, отсутствие нижней границы и суммы призов сохранены.
Автоматической выплаты призов нет.

Логи: `Season rollover started`, `Season snapshot completed`, `Season created`,
`Season rollover completed`; повторная проверка — DEBUG `Season rollover skipped`.

## Установка

Из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

На Linux/macOS путь к Python окружения: `.venv/bin/python`.

## Настройка

Заполните `.env` в корне проекта:

```dotenv
DOTA_ACCOUNT_ID=123456789
OPENDOTA_API_KEY=
TELEGRAM_BOT_TOKEN=
```

`123456789` — пример: замените его своим **Dota account_id (Steam32)**.
Это числовой ID в ссылке `https://www.opendota.com/players/<account_id>`.
SteamID64 и Telegram ID не подходят.

Ключ OpenDota необязателен. `.env` исключён из Git; после клонирования
создайте его по примеру выше. Переменные окружения имеют приоритет над `.env`.

## Telegram-бот

Запишите токен бота в `TELEGRAM_BOT_TOKEN` в `.env`, затем выполните:

```powershell
.\.venv\Scripts\python.exe -X utf8 main.py
```

Без токена программа выводит понятное сообщение и завершается с кодом 1.
Бот получает обновления через polling.

- `/start` — новому пользователю показывает описание Turbo Rating, затем инструкцию
  привязки в одном HTML-сообщении и сразу ожидает код друга через существующий процесс.
  Первый визит сохраняется в `bot_users`, независимо от завершения привязки.
  Повторный `/start` без аккаунта показывает только инструкцию и сохраняет текущие
  данные ввода/повторной проверки. После перезапуска ожидание ввода возобновляется
  без повторного onboarding. Привязанный пользователь сразу видит главное меню.
  Для зарегистрированного — только nickname, текущий TR и место в топе.
- `/add 123456789` — проверка Dota ID через OpenDota и привязка к текущему
  Telegram-пользователю. Сразу инициализирует и показывает стартовый рейтинг.
  Замените пример своим Dota ID.
- `/profile` и `/rating` — один экран «👤 Профиль»: nickname, Dota ID,
  текущий Turbo Rating, место, стартовый и рекордный TR, дата подключения.
  Дата берётся из сохранённого начала отслеживания Dota-профиля, в UTC.
- `/matches` и `/history` — один экран «📜 История матчей»: последние 10
  сохранённых Turbo после подключения за последние 7 дней, от новых к старым. Для каждого — дата
  игры в UTC, WIN/LOSE, имя героя, сохранённое изменение TR и рейтинг после матча.
  При одинаковой дате порядок определяется `match_id`. Калибровочные матчи
  и другие режимы не показываются. Для матча без начисления указано «TR не начислен.»,
  для неизвестного исхода — «Результат пока неизвестен».
  Семидневный фильтр применяется в SQL по `matches.start_time`, включая нижнюю
  границу `now - 7 дней`; старые матчи остаются в БД. Если подходящих матчей нет:
  «За последние 7 дней матчей нет.». Сумм изменений за сегодня, 7 и 30 дней и кнопок
  выбора периода в интерфейсе нет.
- `/sync` — загрузка новых матчей привязанного игрока; после неё `/matches`
  сразу показывает сохранённые игры. Ответ «Обновлено» содержит число новых
  Turbo, WIN/LOSE, изменения и рейтинг до/после. Без начислений —
  «Данные актуальны» и текущий рейтинг. Технических счётчиков в ответе нет.
  Кнопка «🔄 Обновить» и `/sync` имеют общий cooldown 30 секунд на
  Telegram-пользователя, включая разные чаты. После ошибки можно повторить запрос
  сразу. Autosync этим ограничением не затрагивается.
- `/stats` — alias `/rating`, использует тот же обработчик и показывает тот же
  экран. Отдельного экрана и кнопки статистики нет.
- `/top` — до 20 игроков с уже инициализированным рейтингом и хотя бы одной
  текущей привязкой в `telegram_users`, по убыванию
  `current_rating`; при равенстве — по возрастанию `account_id`.
  Каждый Dota аккаунт отображается один раз независимо от числа привязок Telegram.
  Первые три места отмечены медалями, свой аккаунт — «← вы». Если он ниже top-20,
  внизу показано «Ваше место: #N — XXXX TR» с той же стабильной сортировкой.
  После рейтинга показано движение за 7 дней: `↑2`, `↓1` либо `—` без изменения.
  Для игроков, зарегистрированных менее 7 дней назад, индикатора нет.

После регистрации доступна постоянная клавиатура:

```text
👤 Профиль          🥇 Топ
📜 История матчей   💰 Призы
🔄 Обновить         🔁 Сменить Dota
ℹ️ Что такое Turbo Rating?
```

Для непривязанного пользователя показаны кнопки знакомства и призов.
«🥇 Посмотреть топ» открывает тот же список, что и `/top`.
«ℹ️ Что такое Turbo Rating?» повторно открывает тот же HTML-текст, что и onboarding.
Кнопка есть в основном меню до и после привязки; в клавиатуре истории она скрыта.
Чтение описания не отменяет незавершённую привязку. На экране описания inline-кнопка
«ℹ️ Как считается рейтинг» открывает существующую справку; старая текстовая кнопка
тоже продолжает работать. Этот экран
объясняет калибровку по последним 20 Turbo, базовые начисления
WIN → +25 TR, LOSE → -25 TR и бонус до +10 TR за личный вклад.
Например, хорошая игра с бонусом +5 даёт +30 TR за победу или -20 TR за поражение.
Главный экран остаётся кратким; полное описание показывается при знакомстве и по кнопке информации.
Нажмите «➕ Привязать Dota»: экран «Подключение Dota 2» предлагает отправить
код друга Steam обычным сообщением (например, `165682118`) и включить
«Общедоступная история матчей» в Dota 2. Inline-кнопки «🔎 Как найти код друга»
и «⚙️ Как открыть историю матчей» открывают пошаговые инструкции, сохраняя ожидание ввода.
После включения истории данные обновляются не сразу; бот предлагает подождать
и попробовать снова, без конкретного времени ожидания.
Можно отправить ссылку `https://www.opendota.com/players/165682118` или
`https://www.dotabuff.com/players/165682118`. Steam-ссылки и SteamID64
пока не поддерживаются. Парсер находится в `app/services/accounts.py`.

После успешной привязки бот показывает рейтинг, место, стартовый рейтинг и
возвращает основное меню. Если данные аккаунта пока недоступны, бот напоминает
проверить общедоступную историю и показывает «🔄 Проверить снова». Кнопка повторяет
проверку уже введённого кода; повторный ввод не нужен. Она также доступна при
временной ошибке API и при смене аккаунта. Новый ввод, выход из диалога и успешное
подключение делают прежнюю кнопку проверки неактивной. Нажатие другой
кнопки навигации завершает ожидание ID. Для непривязанного пользователя `/start`
продолжает ввод и сохраняет текущую кнопку проверки; описание продукта и справка
через его inline-кнопку также сохраняют ввод. Состояние ввода хранится в памяти
отдельно для пользователя и чата. После перезапуска `/start` снова открывает привязку,
а одноразовое знакомство не повторяется благодаря записи в `bot_users`.
Данные уже привязанного аккаунта остаются в SQLite.

Сообщение со старой подписью «🔗 Поделиться» отправляет короткое приглашение со ссылкой на текущего бота;
это сообщение можно переслать другу. Username берётся из Telegram и кэшируется
клиентом бота, отдельная настройка ссылки не нужна.

При успешном ручном или автоматическом sync nickname обновляется из OpenDota,
если изменился. Время начала отслеживания и привязка сохраняются. Закрытая история
показывается как «Не удалось получить историю матчей. Включите Expose Public Match
Data в Dota 2.», сбой API — «OpenDota временно недоступен. Попробуйте позже.».
Технические сведения об ошибках остаются в logging.

Кнопки используют те же обработчики, что и команды. Общие функции в `app/screens.py`
форматируют экраны из уже загруженных данных, без SQL и пересчёта рейтинга.
`/add` без аргумента
начинает диалог привязки, а для зарегистрированного пользователя — подтверждение
смены. `/add <ID или ссылка>` подключает сразу через тот же сервис.
При запуске бот регистрирует меню `/start`, `/add`, `/rating`, `/history`, `/top`,
`/matches`, `/sync`, `/profile`. Старые подписи «🏆 Рейтинг», «📊 Статистика»
и «🥇 Топ игроков» ещё работают; `/stats` доступна без отдельного пункта меню команд.
Если профиль не привязан, личные разделы предлагают кнопку привязки.

`app/services/heroes.py` загружает `OpenDota constants/heroes` один раз при
запуске с таймаутом 10 секунд и хранит имена в памяти до завершения процесса.
`get_hero_name()` читает только кэш: HTTP-запросов на каждый матч нет.
При сбое загрузки или неизвестном ID используется `Hero #44` (с нужным ID).
Бот продолжает запуск; следующая попытка загрузки будет при перезапуске.

Привязки хранятся в `telegram_users(telegram_id PRIMARY KEY, account_id)`.
Повторный `/add` не создаёт дубликатов и не сбрасывает начало отслеживания.
`/add` с другим Dota ID заменяет текущую привязку; история игроков сохраняется.
Несколько Telegram-пользователей могут ссылаться на одного игрока.

### Смена Dota-профиля

Нажмите «🔁 Сменить Dota» или отправьте `/add` без аргумента.
Бот покажет текущий nickname и Dota ID, затем
inline-кнопки «Сменить аккаунт» и «Отмена». После подтверждения:

```text
Смена Dota-профиля

Отправь новый код друга из Steam.
В Dota 2 включи «Общедоступная история матчей».
```

Поддерживаются Friend ID, OpenDota URL и Dotabuff URL через тот же
`parse_dota_account_id()`. Например, после ввода `123456789` ответ может быть:

```text
Готово.

Теперь подключён:

Stusimba
Dota ID: 123456789

Turbo Rating: 1087
Место: #3
```

После успеха возвращается главное меню; `/profile`, `/rating` и `/stats`
сразу используют новый аккаунт. Пример `/top`, если у старого аккаунта
больше нет Telegram-привязок:

```text
Turbo Rating

🥇 Leader — 1200
🥈 Player Two — 1120
🥉 Stusimba — 1087 ← вы
```

На обоих шагах можно нажать «Отмена», отправить `/cancel` или перейти
в другой раздел меню. Ответ: «Смена аккаунта отменена.», привязка остаётся
прежней. Старые inline-кнопки после закрытия или перезапуска диалога не действуют.
Ошибку ввода или загрузки можно исправить повторной отправкой ID.

Общий сервис `link_dota_account()` в `app/services/accounts.py` используется
диалогом и `/add`. Текущий ID возвращает «Этот Dota-профиль уже подключён.»,
nickname и сохранённый рейтинг без HTTP-запросов и записей в БД.
Для другого ID сначала проверяется профиль OpenDota и подготавливается рейтинг
через существующий `ensure_player()`. Новый игрок получает время начала
отслеживания и стартовый рейтинг по прежней формуле, по максимум 20 прошлым Turbo.
Только после успешной подготовки SQLite UPSERT в одной транзакции меняет
`telegram_users.account_id`. Ошибка проверки, инициализации или записи сохраняет
старую связь. Если загрузка калибровки прервалась, созданный игрок без рейтинга
может быть подготовлен при повторной попытке с тем же временем начала отслеживания.

У существующего игрока сохраняются `tracking_started_at`, стартовый и текущий
рейтинг, калибровка, матчи и история начислений. Данные старого аккаунта также
сохраняются: повторное подключение возвращает прежний рейтинг. Аккаунт без
Telegram-привязок исчезает из `/top` и списка следующего прохода autosync.
Если остался хотя бы один другой Telegram-пользователь, аккаунт продолжает
участвовать в обоих списках и показывается в топе один раз.

`/matches` и `/profile` читают SQLite. `/rating`, `/history` и `/stats` инициализируют отсутствующий
рейтинг через OpenDota, после чего читают сохранённый рейтинг.
Для загрузки новых матчей нажмите «🔄 Обновить» (либо `/sync` или `scripts.test_sync`).
Также загрузка выполняется автоматически, пока работает бот.

### История рейтинга и историческое место

История использует сохранённые `ratings` и `rating_history`, без новых таблиц
и снимков leaderboard. В `app/db.py` доступны `get_rating_at()`, `get_rank_at()`,
`get_peak_rating()`, `get_rating_change()` и `get_leaderboard_at()`.

Время события — `rating_history.created_at`, то есть момент начисления TR.
Если sync догрузил старые матчи сегодня, их начисления входят в сегодняшний
период. События в одну секунду упорядочены по порядку записи в SQLite (`rowid`).
Универсальная функция `get_rating_change()` сохранена, но интерфейс больше не
запрашивает и не выводит суммы за сегодня/7/30 дней. Даты матчей в истории — МСК,
её семидневная граница отсчитывается от текущего времени по `matches.start_time`.
Граница периода включается в выборку. Начальная калибровка не считается
приростом TR, но `initial_rating` всегда участвует в расчёте рекорда.

В текущем сезоне `get_rating_at()` суммирует сохранённые начисления не позднее указанной секунды,
учитывая отдельное время позднего performance, поверх `initial_rating`. До `tracking_started_at`
игрок не участвует в историческом топе. Отсутствующие рейтинг или место возвращаются
как `None`; экран показывает «ещё не зарегистрирован» вместо выдуманной позиции.

Исторический leaderboard открытого сезона включает всех **нынешних** активных игроков с рейтингом,
существовавших на выбранную дату. Сортировка: полный рейтинг по убыванию,
затем `account_id` по возрастанию, как в `/top`. Исторический список не ограничен
20 игроками; экран `/top` по-прежнему показывает 20. История Telegram-привязок
не сохраняется, поэтому место внутри открытого месяца восстанавливается среди текущего состава.
Для закрытых месяцев состав, имена, рейтинги и итоговые места читаются из снимка.

## Автоматическая синхронизация

`main.py` запускает бот и фоновую задачу `app/autosync.py`. Первый проход
начинается сразу при запуске. Затем после каждого прохода задача ждёт
`AUTO_SYNC_INTERVAL_SECONDS = 300` секунд и повторяет цикл.

Синхронизируются только уникальные Dota ID из `telegram_users`, последовательно.
Ошибка одного игрока не останавливает остальных. При завершении polling
задача отменяется и ожидается её завершение; затем закрывается сессия Telegram.

Если появились `rating_updates`, каждый Telegram-пользователь, привязанный
к этому аккаунту, получает одно сообщение за проход. Несколько игр объединяются:
показываются имена героев, отдельные изменения и рейтинг от первого `rating_before`
до последнего `rating_after`. Для одной игры — «🟢 Победа в Turbo»,
изменение TR и рейтинг до/после. В конце уведомления показано изменение места,
например «Место:» и на следующей строке «#4 → #3», либо «Место: #3», если
оно не изменилось. Для нескольких игр показано одно изменение места за всю серию.
При большом числе игр показываются до 50 строк
с ограничением общей длины и количество оставшихся, чтобы сохранить одно сообщение.
Без новых начислений сообщение не отправляется. Ошибка доставки одному
получателю не мешает другим; очередь повторной доставки пока не реализована.

Ручной и автоматический sync используют один сервис. `asyncio.Lock` отдельный
для каждого `account_id`: повторный вызов во время активного sync сразу возвращает
`already_in_progress`, бот отвечает «Обновление уже выполняется». Новые запросы API
при этом не запускаются, cooldown не устанавливается. Разные аккаунты могут
синхронизироваться независимо. Текущий запуск `python main.py` использует один
процесс и один event loop; lock действует в этих пределах. Не запускайте второй
бот или CLI sync одновременно с ним для того же аккаунта: между процессами
блокировка запросов не действует. Транзакции SQLite и уникальный ключ
`rating_history(account_id, match_id)` защищают начисления и в этом случае.

HTTP-клиент использует таймауты connect/read/write/pool = 5/35/10/5 секунд.
GET-запрос повторяется максимум один раз после задержки 0,5 секунды, только при
ReadTimeout, ConnectTimeout и HTTP 500/502/503/504. Ошибки 4xx, остальные статусы,
некорректные JSON/данные и отмена не повторяются. Ошибка профиля, калибровки или
списка матчей прерывает sync; ошибка статистики отдельного матча оставляет
performance в ожидании и не мешает остальным матчам.

Если ручной sync длится больше двух секунд, бот сообщает, что загрузка продолжается.
При таймауте он показывает понятный ответ и разрешает повторную попытку сразу.
Обработчик ожидает результат; отдельная очередь задач не требуется.

Стандартный `logging` выводит запуск/остановку бота и autosync, Dota ID,
число новых матчей и начислений, ошибки синхронизации и уведомлений.
URL запросов с API key не выводятся в журнал.

## Синхронизация в SQLite

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.test_sync 123456789
```

Замените ID своим или опустите аргумент, чтобы использовать `DOTA_ACCOUNT_ID`
из `.env`. Каталог `data` и база `data/turbo_rating.db` создаются автоматически
относительно корня проекта. Дополнительные зависимости для БД не нужны.

При первом запуске игрок получает `tracking_started_at`, равный текущему
Unix-времени. Повторные запуски сохраняют это значение. Скрипт запрашивает
страницы матчей любых режимов и сохраняет только те, у которых
`start_time >= tracking_started_at`. Поэтому первый запуск обычно добавляет
игрока и сохраняет 0 обычных матчей: предыдущие игры старше начала отслеживания.
Отдельно сохраняется до 20 исторических Turbo-матчей для калибровки.

Таблицы: `players` с ключом `account_id` и `matches` с составным ключом
`(account_id, match_id)`. Повторная вставка не создаёт дубликаты.
`save_match` вычисляет результат игрока по `player_slot` и `radiant_win`;
если этих данных нет, результат хранится как `NULL` и выводится как `UNKNOWN`.

Вывод содержит начало отслеживания в UTC, количество полученных, старых,
повторных и новых матчей, новые матчи и общий размер истории игрока в БД.
`fh_unavailable=true` останавливает синхронизацию с ошибкой недоступной истории.
Пустой список матчей без этого признака остаётся допустимым ответом.
База исключена из Git.

Обычная синхронизация читает страницы по 50 матчей с offset до начала
отслеживания или конца доступной истории. Это позволяет обработать игры после
простоя, даже если их больше 20. Последняя страница может включать старые игры,
которые будут пропущены. Обработка рейтинга выполняется по `start_time ASC`.
При повторяющейся странице или превышении защитного лимита 1000 страниц
запуск завершается ошибкой до сохранения новых матчей: история не считается
успешно синхронизированной частично. Полнота зависит от данных OpenDota.
История для калибровки загружается отдельно с offset, страницами по 50 матчей,
не более 10 страниц. Остановка также происходит при наборе 20 подходящих матчей
или неполной странице. Калибровка использует только доступную историю OpenDota.

Общая логика находится в `app/services/sync.py`:

- `ensure_player(account_id)` проверяет профиль через OpenDota и добавляет
  игрока, сохраняя существующее начало отслеживания, и инициализирует рейтинг.
  Используется `/add` и CLI.
- `sync_player(account_id)` работает с уже добавленным игроком и возвращает
  `SyncResult`: `received_count`, `new_count`, `new_matches`, `skipped_old`
  и `skipped_duplicates`, а также `rating_changes` с начислениями этого запуска.
  Дополнительно `rating_updates: list[RatingUpdate]` содержит `match_id`,
  `start_time`, `hero_id`, `win`, `rating_before`, `rating_delta`, `rating_after`, `performance_bonus`,
  `is_correction`. Сначала идут новые начисления от старых матчей к новым,
  затем корректировки performance старых матчей; сумма дельт равна изменению TR
  за этот sync. `performance_pending` — число ожидающих score в недавнем окне,
  `already_in_progress` — признак занятого аккаунта (без начислений в этом ответе).
  `new_matches` содержит сохранённые строки БД с `win`.

Перед использованием сервиса нужно вызвать `db.init_db()` и загрузить `.env`
в точке входа. При необходимости функции принимают необязательный `api_key`.
Сервис не зависит от Telegram и ничего не печатает; SQL остаётся в `app/db.py`.

## Turbo Rating

Математика находится в `app/services/rating.py`:

```text
BASE_RATING = 1000.0
ELO_SCALE = 400.0
CALIBRATION_MATCHES = 20
PRIOR_WINS = 5
PRIOR_LOSSES = 5

p = (W + 5) / (N + 10)
initial_rating = 1000 + 400 * log10(p / (1 - p))

score = 0.30 * kill_participation + 0.20 * hero_damage + 0.15 * tower_damage
        + 0.15 * survivability + 0.20 * support
bonus = 0 if score <= 0.35 else round((score - 0.35) / 0.65 * 10)
bonus = clamp(bonus, 0, 10)
delta = (25.0 if win else -25.0) + bonus
new_rating = current_rating + delta
```

В переходном сентябрьском сезоне начальный рейтинг рассчитывается один раз по самым новым (до 20) Turbo-матчам
с `start_time < tracking_started_at`. Они помечены `is_calibration=1` и не создают
`rating_history`. При отсутствии истории стартовый рейтинг равен 1000.
Результаты без `player_slot` или `radiant_win` не считаются поражениями и
не участвуют в рейтинге; неполные исторические матчи пропускаются.

Для существующих игроков рейтинг лениво инициализируется при `/profile`, `/rating`,
`/stats`, `/matches`, `/history` или `/sync` с первоначальным `tracking_started_at`. Повторные вызовы
не меняют стартовый рейтинг и состав калибровки. Ошибка API не фиксирует
пустую калибровку: следующий вызов может повторить инициализацию.

После регистрации рейтинг меняют только обычные Turbo-матчи (`game_mode=23`,
`is_calibration=0`, `start_time >= tracking_started_at`) текущего открытого сезона с известным результатом.
За один sync они обрабатываются от старых к новым, при равном времени — по
match_id. Остальные режимы сохраняются без изменения рейтинга.
Внутри расчётов используется полная точность, в SQLite — REAL; только отображение
округляется до целого. Бонус округляется до целого при расчёте. GPM, XPM,
last hits, net worth, выбор героя и серии побед не влияют на Performance Score.

Базовые ±25 сначала сохраняются транзакционно, затем `get_match(match_id)` получает
статистику всей команды. Каждый sync повторяет расчёт для записей с
`performance_score IS NULL` среди последних 50 рейтинговых матчей — до 20 матчей
за проход. Неудачные попытки отмечаются временем `performance_attempted_at`
и уступают очередь ещё не проверенным матчам. Старые пропуски за пределами этого
окна автоматически не обрабатываются. Кандидаты берутся из БД независимо от списка
новых матчей API. Рассчитанный score, включая 0, повторно не запрашивается.
Игрок находится по `account_id`, пять союзников — по `player_slot`.
Участие в убийствах — `(kills + assists) / team_kills`, урон героям и строениям —
отношение к максимуму команды, выживаемость — `1 - deaths / max_team_deaths`.
Если у всей команды нет смертей, выживаемость равна 1. Все компоненты ограничены 0..1.
Support состоит из 40% wards (`obs_placed + sen_placed`), 30% camps stacked и
30% hero healing, каждый показатель относительно максимума команды.
Отсутствующие/некорректные значения, включая неполные данные союзников, исключают
соответствующий компонент с перенормированием весов, в том числе внутри support.
Нулевые team kills и максимумы урона делают компонент недоступным.
Реальные нулевые support-показатели дают 0; отсутствующие не подменяются нулями.
Если доступно меньше трёх компонентов, score сохраняется как NULL и бонус равен 0.
Ошибки получения полного матча оставляют score равным NULL и не прерывают sync.
Калибровка и другие режимы не запрашивают полную статистику.

При восстановлении performance в одной SQLite-транзакции обновляются исходная
запись `rating_history` и текущий рейтинг. Прибавляется только разница между новым
и уже учтённым бонусом: например, +25 становится +31, а текущий TR растёт на +6.
База и калибровка повторно не начисляются. Балансы следующих записей сдвигаются
на ту же разницу в порядке их записи. `performance_adjustment` и
`performance_applied_at` сохраняют величину и время позднего начисления, поэтому
исторические рейтинги и изменения за сегодня/7/30 дней учитывают бонус с момента
его получения. Повторная запись завершённого score ничего не меняет.
Корректировки в уведомлениях отмечаются отдельно (`RatingUpdate.is_correction`);
`rating_delta` такого уведомления содержит только добавленный бонус. После
завершения сезона восстановление не меняет зафиксированный рейтинг.

`calculate_rating_delta(win, performance_bonus=0)` возвращает базовые ±25 плюс бонус 0..10.
`calculate_new_rating()` прибавляет delta к текущему TR. Размер изменения
не зависит от текущего рейтинга, места и соперников.
Нижней границы и потолка рейтинга нет.

| Пример | Score / бонус | WIN / LOSE |
| --- | --- | --- |
| Сильный carry | 0.6925 / +5 | +30 / -20 |
| Хороший support | 0.645 / +5 | +30 / -20 |
| Слабая игра | 0.215 / 0 | +25 / -25 |

Новая формула используется для следующих базовых начислений. Сохранённые
`initial_rating`, калибровка и базовые дельты старой формулы не пересчитываются.
Следующее начисление продолжает сохранённый `current_rating`. `init_db()` добавляет
недостающие поля performance через `ALTER TABLE`; миграция повторяема и сохраняет
старые начисления. Пропущенный score восстанавливается при следующем успешном sync
после перезапуска обновлённого приложения, с учётом окна и лимита выше.
В деталях JSON сохраняются пять компонентов (недоступные — `null`). В новых строках
`expected_score` сохраняется техническое значение `0.5`, которое не участвует
в расчёте TR. Старые значения этой колонки сохраняются.

Калибровка и создание `ratings` выполняются одной транзакцией. Новые начисления
и записи `rating_history` также фиксируются одной транзакцией с блокировкой
записи. Пара `(account_id, match_id)` исключает повторное начисление.
Sync обрабатывает также уже сохранённые подходящие матчи без `rating_history`
(например, после сбоя или обновления MVP). Рейтинг игроков одного матча независим.

## Таблицы SQLite

- `players`: `account_id INTEGER PRIMARY KEY`, `nickname TEXT`,
  `tracking_started_at INTEGER NOT NULL`, `created_at INTEGER NOT NULL`.
- `matches`: `account_id INTEGER NOT NULL`, `match_id INTEGER NOT NULL`,
  `start_time INTEGER NOT NULL`, `game_mode INTEGER`, `hero_id INTEGER`,
  `player_slot INTEGER`, `radiant_win INTEGER`, `win INTEGER`, `duration INTEGER`,
  `created_at INTEGER NOT NULL`, `is_calibration INTEGER NOT NULL DEFAULT 0`.
  Первичный ключ — `(account_id, match_id)`.
- `telegram_users`: `telegram_id INTEGER PRIMARY KEY`,
  `account_id INTEGER NOT NULL REFERENCES players(account_id)`.
- `bot_users`: `telegram_id INTEGER PRIMARY KEY`, `created_at INTEGER NOT NULL`.
  Запоминает посетителей до завершения привязки; создаётся через `CREATE TABLE IF NOT EXISTS`.
  Существующие привязки также считаются известными пользователями без повторного onboarding.

```sql
CREATE TABLE ratings (
    account_id INTEGER PRIMARY KEY REFERENCES players(account_id),
    initial_rating REAL NOT NULL,
    current_rating REAL NOT NULL,
    calibration_matches INTEGER NOT NULL,
    calibration_wins INTEGER NOT NULL,
    initialized_at INTEGER NOT NULL,
    season_id TEXT
);

CREATE TABLE rating_history (
    account_id INTEGER NOT NULL REFERENCES ratings(account_id),
    match_id INTEGER NOT NULL,
    rating_before REAL NOT NULL,
    expected_score REAL NOT NULL,
    result INTEGER NOT NULL,
    rating_delta REAL NOT NULL,
    rating_after REAL NOT NULL,
    created_at INTEGER NOT NULL,
    performance_score REAL NULL,
    performance_bonus INTEGER NOT NULL DEFAULT 0,
    performance_details TEXT NULL,
    performance_attempted_at INTEGER NULL,
    performance_applied_at INTEGER NULL,
    performance_adjustment REAL NOT NULL DEFAULT 0,
    season_id TEXT,
    PRIMARY KEY (account_id, match_id),
    FOREIGN KEY (account_id, match_id) REFERENCES matches(account_id, match_id)
);
```

`init_db()` добавляет недостающую колонку `matches.is_calibration` и поля performance через
`ALTER TABLE` после проверки `PRAGMA table_info`. Существующая БД, игроки,
привязки и время начала отслеживания сохраняются. Новых зависимостей нет.

## OpenDotaClient

```python
from app.services.opendota import OpenDotaClient

async def example(account_id: int):
    async with OpenDotaClient() as client:
        player = await client.get_player(account_id)
        matches = await client.get_recent_turbo_matches(account_id, limit=10)
    return player, matches
```

Методы возвращают JSON как `dict` / `list[dict]`. Клиент использует таймаут
20 секунд, вызывает `raise_for_status()` и закрывает соединения при выходе
из `async with` (либо через `await client.aclose()`).

Запросы:

- `GET /players/{account_id}` — данные игрока.
- `GET /matches/{match_id}` — полная статистика только для ещё не начисленных Turbo-матчей.
- `GET /players/{account_id}/matches?game_mode=23&limit=10&significant=0&sort=start_time`
  — последние доступные Turbo-матчи.
- `GET /players/{account_id}/matches?limit=20&significant=0&sort=start_time`
  — последние матчи любых режимов через `get_recent_matches`.

`significant=0` отключает стандартное исключение матчей, не учитываемых в
статистике OpenDota, включая Turbo. API key, если задан, передаётся параметром
`api_key`. Фильтрация и ограничение количества выполняются на стороне API.

Источники: [спецификация OpenDota API](https://api.opendota.com/api),
[режимы игры OpenDota](https://github.com/odota/dotaconstants/blob/master/json/game_mode.json),
[асинхронный клиент httpx](https://www.python-httpx.org/async/).
